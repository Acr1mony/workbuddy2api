# 架构与设计取舍

这份文档解释「为什么长这样」。想改代码之前读一遍，能省掉几个已知的坑。

## 一句话结构

```
客户端 ──/v1/chat/completions──> routes_openai ──> service ──> pool ──> upstream ──> 腾讯上游
                                                    │        └──> sticky（会话亲和）
                                                    ├──> adapters.chat（请求/响应改写）
                                                    ├──> authflow（令牌）
                                                    └──> usage（台账）
面板浏览器 ──/api/*──> routes_admin ──> 上面那些模块的只读/管理视图
```

`service.py` 是唯一的编排者：它拿 `Request`、选出账号、改写请求、打上游、把 SSE 重写成 OpenAI 格式、记账。HTTP 层（`httpserver.py`）不认识业务，业务层不认识 HTTP。

## 为什么是「零依赖的标准库」

两个参考实现里，Python 那个是 7000 行单文件、Go 那个要编译工具链。零依赖的收益很具体：

- 部署 = 复制目录 + `python -m wb2api serve`，没有 `pip install`、没有虚拟环境、没有 wheel 兼容问题；
- 目标机器可能根本装不上 pip（内网、旧 Python、受限权限）；
- 依赖少 = 供应链面小，这类"反代"项目要处理别人的 token，越少第三方代码越好。

代价是自己写了 300 行 HTTP 框架（`httpserver.py`）：只支持 HTTP/1.1、不支持 keep-alive 之外的复用细节、SSL 交给前置 nginx/caddy。够用，而且出问题能读得懂。

## 一次 chat 请求的完整路径

1. **鉴权**：`Authorization: Bearer <key>` 或 `X-API-Key`。没有配置任何密钥时进入"开放模式"（只建议在 `127.0.0.1` 上这么用）。
2. **定域**：`cn:` / `global:` 模型名前缀 → 密钥绑定 → `X-Realm` → `?realm=` → 默认 `cn`。
3. **改写请求**：`chat.prepare_request()`，顺序固定（见 `docs/PROTOCOL.md` §2）。顺序不能随便动：比如工具配对必须在 `thinking` 注入之前，否则回填 `reasoning_content` 会打断配对判定。
4. **选号**：会话亲和优先 → 池策略（加权随机/轮询/顺序耗尽）→ 成本层过滤 → 并发槽。
5. **打上游**：`identity.chat_headers()` 造一整套会话头，`upstream.post(raw_body=...)` 直接发预编码字节（不能重新 `json.dumps`，紧凑分隔符本身就是指纹的一部分）。
6. **失败处理**：`_absorb()` 把错误归类到池的记账动作，返回"是否换号"。**流式一旦开始写响应头就不能换号。**
7. **回写**：流式把上游 SSE 逐帧重写成 OpenAI chunk；非流式在本地聚合成一个 `chat.completion`。
8. **记账**：一行 JSONL，`finally` 里写（客户端中断也写，上游已经计费了）。

## 二十个关键决定

### 1. 冷却窗口持久化，失败叙述不持久化

账号的 `cooldown_until`、`breaker_until`、`restricted_until` 等**时间窗**写盘；`last_error` 这类**文字**只留在内存。

原因很实际：如果一个 429 早已恢复，但它的错误文字被持久化，重启后面板仍然显示"限流中"，人会去查一个不存在的问题。窗口是事实，叙述是当时的解释。

窗口到期不等于"真的恢复"：402/`6004` 把账号挂到重置点之后，本地没有任何证据说明额度回来了。所以 `quota_probe` 任务（每 10 分钟一跳）会在**解禁点 + 60 秒**主动打一发 `max_tokens=16` 的最小请求：通了就 `note_success` 清窗（"真跑通了"是唯一证据），没通就退到 6 小时后再探。让探测花 16 个 token，好过让用户的第一个真实请求去撞墙并被记一次失败。

### 2. 风控（403 / `11140`）绝不换号

参考实现的实测结论：同一份请求在一轮里轮换号码，把 7 个账号**连着**封了。风控是按内容/指纹判定的，换号只是在扩大伤害面。所以：

- `11140` → 该号冷却 2 小时，**不换号**，直接把 403 返回客户端；
- 900 秒内有 2 个不同账号被风控 → 整个域暂停 30 分钟（`pool.restriction_hold_seconds`）。

同理，`11-128`（指纹/渠道）也是"改内容"能过、"换账号"没用的问题，所以不换号。

判定入口特意做得很宽：先把 body 反转义（最多三层），再用 `"code"\s*:\s*"?11140"?` 正则匹配，另外还认 `账号存在异常行为` / `已被限制` / `unusual activity` 这几个文案。**漏判一次就要换号，而换号就是连坐**，所以宁可误判成受限。

### 3. 403 有三种，处置方式相反

原来的实现把 `403` 一律当"凭证失效"——换号 + 强制刷新。这是最贵的一个错误：一次 WAF 风暴会让每个账号的刷新端点都被打一遍（参考实现记录过"四小时 196 次传输失败，关掉 13 个账号"）。现在是三路：

| 判据 | `kind` | 处置 |
|---|---|---|
| body 里有 `11140` | `restricted` | 冷却 2 小时，**不换号** |
| body 不是 JSON 信封（HTML 错误页）或命中审核文案 | `waf` | 软避让 60 秒（`pool.waf_cooldown`），**不刷新凭证、不换号、不写受限** |
| 其余 403 | `auth` | 刷新令牌再用同一个号 |

`waf` 单独存在的意义是：内容审核跟账号健康毫无关系，换号照样被拦，而"换号继续打"正是风控最想看到的形状。

### 4. 链路抖动记在"出口"上，不记在账号上

`5xx` / 超时不再让账号进熔断，而是记在 `(host, proxy)` 这个**出口**键上（`wb2api/egress.py`）：1s 起、指数增长、15s 封顶、±25% 抖动、60 秒无错清零。

两个理由：

1. 一次 CDN 抖动如果记到账号上，整池会同时熔断，可用性直接塌方；而运维看到"账号全在冷却"会去重登、换号、加号——全是白费功夫。
2. 退避必须带抖动。多个线程同时退避、等待时长完全一样时，它们会在同一毫秒一起回来，对上游来说那就是一台机器在整点打卡。

超时还额外有一条：**不换号、不重试**。同一份请求换个号只会再撞一次慢上游，而重发很可能让上游再生成一遍（重复计费）。所以超时直接 503 `upstream_timeout`。

### 5. 连接池按凭据分池，半读连接不回池

池键是 `scheme://host:port|proxy|sha256(Authorization)[:16]`。同一个 TCP 连接上先后出现两个 `Authorization`，在上游看来就是"多套设备共用一条链路"，这是最直接的跨号关联线索。

另外，只有**整段 body 已读完**的响应才允许回池（`_reusable()` 要求 `_consumed`）：半读的连接里还留着上一条流的残帧，放回去会让下一个请求读到别人的数据。闲置超过 90 秒的连接直接丢弃并探活（`select` 判 EOF）——WAF 风暴之后上游会常态性掐闲置连接。

### 6. "没有可用账号" 返回 503，不是 429

429 的语义是"你太快了，等会儿再来"，客户端会按退避重试；而池空是"现在没有资源"，重试没意义。混用这两个码会让客户端在半分钟内打几百次空请求。所以本项目里：429 只用于真的限流，池空/上游超时/账号认证失败都用 503，并且**从不返回 504**。

有明确等待时长时（限流解禁、出口退避），响应带 `Retry-After`：不给这个头，客户端会立刻重试，把墙撞穿。

### 7. 会话亲和优先于负载均衡

上游有 prefix 缓存。实测数据（来自参考实现）：没有粘滞时首字延迟 1.5s → 5-6s，且 59% 的 prompt token 白烧。所以选号顺序是"先看这个对话上次用哪个号"，命中就继续，只在失败时 `demote` 掉那一个（其余候选保留——它们的缓存里可能还有这个对话）。

流式路径曾经漏了这一步（`finally` 里用空 body 算会话键，永远是空串 = 永不绑定）。流式是主路径，所以这个 bug 的实际效果是"亲和从未生效"。

粘滞不能无限期：一段连续几十轮的对话钉在同一个账号上，是上游最容易识别的形状（同一 machine id + 同一 session id + 长时间高频）。所以 `session_sticky.page_size`（默认 3）让一个会话在一个号上跑满 3 轮就把队头挪到队尾，下一个请求换人。代价是这一页的 prefix 缓存作废，收益是不让单个账号被一段长会话占死；只有 1 个可用号时不会轮转（换了也是它）。含图片/音视频的请求**不绑亲和**——媒体请求在上游走的是另一条更敏感的审核链路，绑得越死风险越集中。

### 8. 令牌刷新必须单飞

refresh token 是**一次性**的：两个线程同时刷新，第二个拿着已消费的 token 去换，返回 `12153`，整条链失效、账号废掉。`AuthFlow` 用 `util.KeyedLock` 按账号串行化，并且刷新成功后立刻落盘。

保活只提前 **6 小时**续（不是 48 小时）：每刷一次都是一次风险，所以"快到期才刷"比"反复提前刷"安全。

### 9. 面板关闭时路径 404，而不是 401

`panel.enabled=false` 时 `/panel` 与 `/api` **完全不注册**。返回 401 等于告诉扫描器"这里有个需要密码的后台"，404 什么都不说。同理，面板返回的账号行永远不含 token（`Account.masked()`）。

另外两条防封细节：

- **账号之间错峰**：签到/余额刷新在账号之间随机停 1~3 秒。整点把全池打一遍 = 同一出口 IP 上的一次尖峰，那正是风控在找的形状。
- **UA 只有第二段按域切换**：`WorkBuddy/5.5.4 WorkBuddy AI/5.5.4 CLI/2.137.1`。两段都写平台名会得到一个官方从不发出的 UA。

### 10. 只有"用户自己写的话"值得重试，改写用户的话不值得

内容审核打回（403 `content_blocked`）时，网关会摘掉 `system` 消息、换一句中性最小提示词再发一次——因为被盯上的通常是"你是个 Claude Code 之类的身份设定"，而不是用户真正想问的事。用户消息、工具定义、参数一个字节都不改：改了就是在替用户说话，请求也可能因此变成另一个问题。

这条重试**只做一次**，并且这一发不记账号的账（同一个号的第二发不该背冷却）。系统提示词本来就是我们自动补的那句中性话时直接不重试——原样重发只是白烧一次风控计数。

同理，**媒体请求不绑会话亲和**：同一张图被反复提交和多轮对话无关，把它钉在一个号上只会让这个号的请求画像更反常。

### 11. 并发槽在 `finally` 里还，而不是在成功分支里

`max_in_flight` 默认只有 3。少还一次，这个账号就少一个名额；漏三次，整个域永远是 `503 no_account`，只能重启进程——而它不会报错，只会"越来越没有账号可用"。

所以非流式的聚合整段包在 `try/finally` 里，流式的生成器 `finally` **第一件事**就是 `pool.release()`（记账、绑亲和都排在它后面，各自 `try` 包住）；`httpserver` 在响应结束时显式 `resp.stream.close()`，客户端半路断开也能立刻触发那个 `finally`，不用等 GC。

同一原则适用于退避：出口退避等待被限制在 2 秒内，且**不占用槽位做长睡**——持槽睡 15 秒 × 3 个并发就等于把这个域锁死。

### 12. 状态文件坏了就拒绝启动，不要"降级成默认值"

`accounts.json` 解析失败时如果回落成空库，下一次保存会把空库写回去——账号全没了，而且日志里只有一行 warning。`config.json` 更糟：回落默认值意味着 `api_key` 变成空（无鉴权开放）、面板密码变回 `admin`。

现在的行为是：解析失败 → 原文件改名 `.corrupt-<时间戳>` 保留 → 抛 `CorruptFile` → CLI 打印备份路径并以 2 退出。**能自动恢复的数据才叫数据，恢复不了的要让人看见。**

### 13. 面板是"同源页面"，不给跨源许可

客户端面（`/v1/*`）保留 `Access-Control-Allow-Origin: *`，因为本地工具要直连；面板页面则相反：不发 CORS，改发 `X-Frame-Options: DENY` + `Referrer-Policy: no-referrer` + 一条不允许外联的 CSP。面板持有的是"能改密码、能导出明文令牌"的权限，它不该被任何第三方页面嵌进 iframe。

同理 `X-Forwarded-For` 默认**不认**（`server.trust_proxy=true` 才认）：无条件相信这个头，登录限流就形同虚设——换个头就是一个新的 IP。

## 数据目录

```
data/
  accounts.json     账号（含 token —— 这是本项目的最高机密，注意文件权限）
  api_keys.json     客户端密钥（含 models / realm 绑定）
  runtime.json      运行态：面板签名密钥、池游标
  catalog-<realm>.json  模型目录缓存（1 小时有效，重启不必再打一次上游）
  usage/
    usage-YYYY-MM-DD.jsonl   每请求一行，保留 N 天（默认 7）；单文件满 64MB 滚成 .p001.jsonl
  credits/
    credit-YYYY-MM-DD.jsonl  每次刷新余额记一行（总额/到期桶/包数/来源），保留 30 天
  requests/
    req-YYYY-MM-DD.jsonl     逐请求明细，保留 3 天（内存环形另留最近 500 条）
  dumps/
    dump-YYYY-MM-DD.jsonl    失败报文（脱敏、8KB 截断、每天最多 200 条），保留 3 天
logs/
  wb2api.log        滚动 8MB × 5
```

模型目录落盘是刻意的：这份清单只在"客户端会怎么想"的意义上有用，重启一次就重打一次上游纯属白给暴露面。缓存的 `fetched_at` 超过 `CACHE_TTL`（1 小时）就当作不存在，`invalidate()` 会连文件一起删——内存清了磁盘不清，下次启动又会捡回旧清单。

写盘全部走 `util.atomic_write_json`（同目录临时文件 + `os.replace`），断电不会留下半截 JSON。台账用单次 `os.write` 追加，因为读方是 `except: continue`，**丢一行比写坏一行更糟**。

### 14. 台账在独立线程里写，并且按大小分片

请求线程只负责把一行事件塞进队列（`usage.Queue`，上限 2 万条），由一个 `usage-writer` 线程成批 `write + fsync`。理由：`fsync` 是毫秒级的阻塞，放在请求线程里就等于把所有并发串行化了；而队列满了也不丢数据——退回同步写（`inline_fallbacks` 计数），"慢一点"比"账少了"好。

单日文件到 64MB 就滚成 `usage-YYYY-MM-DD.p001.jsonl`。判断阈值必须**按行累加**：一批 400 条 4KB 的记录一次写 1.6MB，如果只在批前检查一次大小，文件会永远不滚。

`close()` 必须投毒并等队列排空（`join(timeout=5)`）——异步化之后"进程退出顺手 `flush()`"会丢掉最后几条。

### 15. 余额看"什么时候过期"，不只看总数

上游把额度拆成几十个资源包，到期日各不相同。只记一个总数会有两个盲点：看起来还有八千，下周最大那个包到期就直接归零；数字掉了三千，分不清是花掉的还是过期的。

所以 `credits.py` 做三件事：解析成结构化清单（字段取不到就跳过，**不猜**）、按到期日分五桶（3 天 / 7 天 / 30 天 / 更远 / 已过期，`total` 只算未过期的）、每次刷新写一条 `credits/credit-*.jsonl` 台账（`spent` 只累加下降段，签到回补不算消耗）。面板据此显示"7 天内到期 4306"和"最近 7 天净变化"。

余额读不到时返回 `None` 而不是 `0`：`0` 会让 `credit_floor` 把一个好账号踢出池子，也会在面板上显示"已欠费"。

### 16. 出口是独立的一层，和账号互不牵连

上游看的形状是"机器 id + 出口 IP"。一个出口被 WAF 盯上时，换账号没有用——出口没换。所以 `proxies.py` 按 `(host:port, proxy)` 分桶，坏掉的出口冷却 5 分钟起、翻倍封顶 1 小时，**全部出口都在冷却时宁可排队等第一个解禁，也不退回直连**：直连等于把真实 IP 交出去，那比慢几十秒贵得多。

同理，账号自带 `proxy` 时优先用它（一条账号绑一个出口，画像更稳），池里的出口只服务没绑的账号。

### 17. 失败报文要留，但只留"要命的那些"，而且必须脱敏

上游拒绝时的原文（`11101` 工具形状、`11129` schema、`11148` 工具配对……）在归一化成 `code` 之后就没了，排障只能靠猜。`diagnostics.py` 把 **body 非空**的失败原文留下来，同时上三道锁：请求头脱敏（`authorization`、`cookie`、`x-refresh-token` 一律 `**redacted**`，body 里的 `sk-` 串也打码）、body 截到 8KB、每天最多 200 条。第三条是关键——错误循环刷的时候，留存不能跟着雪崩，否则磁盘先死。

### 18. 同一个账号同时只跑一条请求

`max_in_flight` 限制的是"整个池"，一个人开三个客户端就能让同一个账号并发三条——在上游眼里这就是脚本。`pool.select()` 因此先拿**账号级锁**再占并发槽：拿不到就分段等到 `serialize_wait`（默认 10 秒），超时返回 503 `no_account`，而不是换个号悄悄继续（换号会把"并发刷"变成"多号并发刷"，更糟）。这个锁是进程内的，多进程部署时它保护不了你——这是已知取舍。

### 19. 配置键有审计，不靠人眼

这个仓库出过好几次"改了配置等于没改"：键名拼错、面板写进一个没人读的键、默认值里留着上一版的名字。这类 bug 的共同点是**不报错**——用户把 `stream_heartbeat_seconds` 改成 5，什么都不会发生，也不会有人知道。

所以 `tools/audit_config.py` 把 `DEFAULTS` 的叶子键和代码里的读取形状做差集，CI 每个矩阵都跑，有死键直接红。工具刻意**宁可漏报**（`cfg.get("上游段", {})` 这种整段读取会把子键都算作已使用），因为误报会逼着人给工具加白名单，最后工具形同虚设。配套的还有一条：接入的键必须有行为，`shutdown_grace` 这种"读到但没用"的也要接上，否则等于换了个名字的死键。

### 20. 长连接由心跳和优雅退出共同维护

流式响应期间上游可能长时间不出字（思考、长上下文排队）。如果什么都不发，中间的反代、NAT、客户端超时都可能把它判死——所以 `stream_heartbeat_seconds` 到点就往客户端写一行 `: keepalive`。两个细节都是坑：心跳**不能算首字延迟**（否则面板上的 TTFT 变成"你配的心跳间隔"，越调越好看、越假）；心跳只能由独立的泵线程产出（上游 `read()` 阻塞时同线程没法同时计时）。

退出也一样：`SIGTERM` 直接杀进程会让正在生成的回答断在半句。`shutdown_grace` 期间 `GatewayServer` 用 `enter_request()`/`leave_request()` 的在途计数等请求写完，等不到就记一条 `还有 N 个请求没写完` 再退出——**宁可留一条日志，也不要静默截断**。

## 模块边界

| 模块 | 可以依赖 | 不该做的事 |
| --- | --- | --- |
| `httpserver.py` | 标准库 | 不认识业务名词 |
| `identity.py` | `util`, `config` | 不发请求 |
| `upstream.py` | `util`, `config` | 不重试、不选号（重试属于 service） |
| `adapters/chat.py` | `util`, `markup`, `sanitize` | 不做 IO |
| `pool.py` | `store`, `sticky`, `util` | 不发请求（只记账） |
| `proxies.py` | `util`, `config` | 不选账号、不发请求 |
| `diagnostics.py` | `util` | 不解读报文（只脱敏、截断、留存） |
| `reqlog.py` | `util` | 不做聚合统计（那是 `usage.py` 的事） |
| `errors.py` | `upstream` | 纯函数，不碰账号、不碰池、不碰磁盘 |
| `relay.py`（`RelayMixin`） | `sse`, `adapters.chat`, `errors` | 不选号、不换号 |
| `failover.py`（`FailoverMixin`） | `pool`, `errors`, `egress`, `proxies` | 不写 SSE 帧 |
| `service.py` | 以上全部 | 不碰 `Request` 以外的 HTTP 细节 |
| `routes_*.py`, `web/` | `httpserver`, `service` | 不直接打上游 |
| `scheduler.py` | `service` | 不起第二个 HTTP 服务器 |

新增能力时先问"它属于哪一层"：改写请求体 → `adapters/chat.py`；新的上游端点 → 各自模块 + `service` 里的方法；新的管理操作 → `routes_admin.py`。

`service.py` 曾经长到 1298 行（约定是 700），2026-11 按"谁会读这段代码"拆成三块：`relay.py`（流式转发 + 记账，改这段的人关心的是帧和台账）、`failover.py`（错误处置，改这段的人关心的是"这个码要不要换号"）、`errors.py`（错误翻译，纯函数，可以脱离网关单独测）。`GatewayService(RelayMixin, FailoverMixin)` 多继承接回去，调用方与测试的 import 路径都不变。`tests/test_request_id.py::ModuleLayoutTest` 守着两条线：`service.py` 不许再超过 700 行，方法名不许在 service 和 mixin 里各写一遍（MRO 会静默选一个，是最难查的那种 bug）。

## 已知取舍与未尽事项

- **面板会话是 `X-Panel-Token` 令牌**，不是 cookie 优先；cookie 也支持（`wb2a_panel`），为了兼容 `curl` 调试。令牌是 HMAC 签名，进程重启后仍有效（密钥在 `runtime.json`），改密码后旧令牌失效需重新登录——这一条依赖密钥轮换，当前实现不轮换，属已知弱点。
- **没有多进程共享状态**。池游标、亲和表都是进程内内存。要跑多实例请让它们各自持有不同的账号子集，或用前置负载均衡做会话粘滞。
- **模型目录缓存 1 小时**，负缓存 5 分钟。换号后目录可能短暂滞后。
- **真机端到端未自动化**：单测覆盖到"没有账号 → 503"为止；带真实 token 的端到端需要人工跑（见 `docs/DEPLOY.md` 末尾的自检清单）。
